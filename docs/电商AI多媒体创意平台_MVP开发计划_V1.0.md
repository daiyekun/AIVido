## 1 计划概述

### 1.1 编制依据与上游基线

本计划是对需求说明书第 12 章「交付里程碑」的**可执行化展开**：上游给出 5 个阶段与 9 周总量，本计划补齐任务编号、工作量、依赖、产出物、验收标准与风险，使其可直接用于排期与进度跟踪。

两份上游文档已完成交叉一致性校验，可作为开发基线，无需再做口径澄清：

| 校验项 | 结果 |
| --- | --- |
| PostgreSQL DDL 两份文档逐字一致 | 通过（各 9863 字符） |
| DDL 在 PostgreSQL 16 实际执行 | 通过（7 表 / 5 触发器 / 7 外键 / 7 约束） |
| 任务状态枚举两侧一致 | 通过（6 态） |
| MySQL 语法残留 | 0 处 |
| 上传通道口径 | 两文档一致（后端中转，无预签名直传） |

### 1.2 计划目标与成功标准

**目标**：用 9 周（按 1 后端 + 1 前端配置）交付一个可上线运行、可持续承接 V1.0 迭代的 MVP。

MVP 完成的成功标准（全部满足才算达成）：

1. 用户可以完成注册、登录，并在前端看到自己有权访问的全部功能；
2. 用户在前端只面对「生成图片」「生成视频」两类入口，细分任务类型由后端推断，用户无感知；
3. 六类生成能力全部跑通真实第三方模型：文生图、图 + 文字生图、文生视频、视频生视频、视频修改生成、图片生视频；
4. 底层模型可在后台配置替换，前端下拉选择，切换模型不改业务代码；
5. 同一会话内每轮对话可独立切换模型；
6. 后台可维护系统提示词模板，业务侧自动匹配并记录 `system_prompt_id`；
7. 任务具备 6 态管理、分级延迟重试（3 次）、取消（仅排队中）与结果预览下载；
8. 任一请求可通过 `trace_id` 贯穿接口、任务表、消息表与日志；
9. 第 11 章 T01–T26 全部场景通过或记录已知偏差；
10. 一套 `docker-compose up` 可在干净机器上拉起全部组件并跑通主流程。

### 1.3 冻结口径（开发基线）

以下口径在开发期间**不得擅自变更**，变更须走变更流程并同步回两份上游文档：

| 基线项 | 取值 | 来源 |
| --- | --- | --- |
| 后端语言与框架 | Python 3.11 + FastAPI 0.115+ + Uvicorn 0.32+ | 需求 §3.3、架构 §2.1 |
| ORM 与迁移 | SQLAlchemy 2.0（async）+ asyncpg + Alembic 1.13+ | 架构 §2.1、§2.2 |
| 任务框架与 Broker | Celery 5.4（`celery[amqp]`）+ RabbitMQ 3.13 | 架构 ADR-002 |
| 结果后端与缓存 | Redis 7（缓存、限流、锁；**不承载业务数据、不做消息队列**） | 需求 §3.3 |
| 关系型数据库 | PostgreSQL 16（7 张业务表） | 架构 ADR-001 |
| 对象存储 | MinIO，4 桶：`ai-input`（7 天过期）/ `ai-output` / `ai-thumb` / `ai-backup` | 架构 §6.2.1 |
| 链路追踪 | OpenTelemetry SDK 1.27+，Span 导出到结构化日志，**不部署 Collector** | 架构 ADR-004 |
| 日志 | structlog / python-json-logger，字段 `timestamp` / `level` / `message` / `trace_id` / `user_id` / `duration_ms` | 需求 §4.4、架构 §14.1 |
| 任务状态机 | `pending` / `queued` / `running` / `success` / `failed` / `canceled` | 需求 §8.7 |
| 失败处理 | 自动重试 3 次（30 秒 / 2 分钟 / 10 分钟），重试期间保持 `running`，前端只显示「生成中」 | 需求 §8.7 |
| 素材上传 | 全量后端中转（`multipart/form-data` 流式写 MinIO），**不提供**预签名直传 | 架构 ADR-003 |
| 管理员机制 | `sys_user.is_admin` 布尔标识，复用手机号 + 验证码登录，`require_admin` 依赖校验 | 架构 §6.1.2 |
| 前端信息架构 | 仅「生成图片」「生成视频」两个大类，不向用户暴露细分生成类型 | 需求 §6.4 |
| 单次生成数量 | 固定 1 张 / 1 个（接口预留 `n` 字段，MVP 只接受 `n=1`） | 需求 §10.15 |
| 素材规格 | 图片 JPG / JPEG / PNG / WebP；视频 MP4 / MOV ≤ 200 MB | 需求 §6.4.1、§6.4.2 |
| 队列优先级 | **默认不启用**（无加急 / 付费插队场景） | 架构 §7.5、§18.2 Q5 |

**MVP 不做**（写入代码即视为缺陷，详见需求 §10）：电商专用工具（商品套图 / 抠图 / 换装）、模板市场、完整资产库、真实支付扣费、会员体系、工单与课程、企业准入审核、完整 RBAC、会话流式输出与导出、提示词变量渲染与版本回滚、多素材上传、任务记录删除、预签名直传、会话内意图自动识别、批量生成。

## 2 工作量估算与人力配置

### 2.1 估算方法与单位

- 单位：**人日**（1 人日 = 1 名工程师 1 个标准工作日，按 8 小时计，已包含编码、自测与代码评审）；
- 估算口径：**不含**需求文档 V0.1–V0.5 撰写（已完成）、不含项目管理与例会（按 10% 隐含在缓冲中）、不含上线后运维；
- 估算是「理想投入」，实际排期需叠加第 3.1 节的缓冲；
- 阶段五的联调、回归与验收归为「共用人日」，由前后端共同投入。

### 2.2 工作量汇总

| 阶段 | 周期 | 后端人日 | 前端人日 | 共用人日 | 合计 |
| --- | --- | --- | --- | --- | --- |
| 阶段一 项目底座与账号体系 | W1–W2 | 13.0 | 0.0 | 0.0 | **13.0** |
| 阶段二 图片生成链路 | W3–W4 | 10.5 | 4.5 | 0.0 | **15.0** |
| 阶段三 视频生成链路 | W5–W7 | 6.0 | 4.5 | 0.0 | **10.5** |
| 阶段四 会话多轮对话 | W8 | 6.0 | 2.5 | 0.0 | **8.5** |
| 阶段五 联调与测试 | W9 | 1.5 | 0.0 | 5.5 | **7.0** |
| **合计** | **9 周** | **37.0** | **11.5** | **5.5** | **54.0** |

**解读**：

- 后端 37 人日 ÷ 5 = 7.4 周；前端 11.5 人日 ÷ 5 = 2.3 周（但受联调节奏约束，不能压缩到 2.3 周完成全部交付）；
- 54 人日与上游「9 周」的对应关系是：**1 后端（7.4 周负荷）+ 1 前端（间歇投入）+ 1 周联调窗口** = 9 周；
- 阶段一是**串行瓶颈**（13 人日集中在同一人身上且任务间强依赖），是决定总工期的关键路径起点。

### 2.3 人力配置方案

| 方案 | 人力构成 | 预估总工期 | 适用场景 | 风险 |
| --- | --- | --- | --- | --- |
| **方案 A（推荐，对应上游 9 周）** | 1 后端 + 1 前端 | **9 周** | 标准配置，前端可间歇投入（W3 起） | 后端单点，无备份人力；后端请假即整体顺延 |
| **方案 B（单人全栈）** | 1 人全栈 | **11 周** | 个人项目或前期验证 | 无并行度，阶段二起前后端切换频繁；无代码评审 |
| **方案 C（加速交付）** | 2 后端 + 1 前端 | **6 周** | 有硬性上线日期 | 需在 W1 投入 2 人同时做底座；接口需提前冻结，协作成本上升 |

**方案 C 的压缩逻辑**：阶段一 13 人日由 2 人并行压到 5–6 工作日（1.1/1.2/1.4 与 1.3/1.5/1.6 分组），阶段二、三、四可部分并行，阶段五保持 1 周窗口。

### 3.3 里程碑验收门（Gate）

每个里程碑必须**全部满足**下列条件才允许进入下一阶段，不允许「带缺陷推进」：

**M1 底座可运行**

- [ ] `uvicorn app.main:app` 可启动，`/docs` 可访问，分层目录与架构 §5.1 一致；
- [ ] 在干净 PostgreSQL 16 执行 Alembic 迁移后：7 张表、5 个触发器、7 个外键齐备；对任意表执行 `UPDATE` 后 `update_time` 自动前进；
- [ ] `init_mq_topology.py` 重复执行幂等；三类业务消息可分别被对应队列消费；
- [ ] 一次请求的日志中 `trace_id` 与响应体一致；
- [ ] 注册、登录、登出可用；非管理员访问 `/api/v1/admin/**` 返回 403；
- [ ] 后台新增模型并启用后，普通用户模型列表立即出现；禁用后立即消失（历史任务仍可追溯）。

**M2 图片可用**

- [ ] 「生成图片」不上传素材 → `task_type=txt2img`；上传图片 → `task_type=img2img`；
- [ ] 上传视频到图片入口被拦截；
- [ ] 绕过前端提交不支持的档位被后端拦截且不进入队列；
- [ ] 任务全链路状态可见，产物可通过签名 URL 预览与下载；
- [ ] 可重试错误自动重试 3 次且前端始终显示「生成中」；3 次失败后置 `failed` 并可复制 TraceID。

## 6 前后端并行协作策略

### 6.1 接口冻结节点

前端不能在接口定稿后才开工，否则 W9 联调必然爆炸。约定三个冻结节点：

| 节点 | 时间 | 冻结内容 | 冻结方式 |
| --- | --- | --- | --- |
| 冻结一 | W2 末 | 用户、模型列表、后台管理类接口 | OpenAPI 文档 + 字段说明 |
| 冻结二 | W3 末 | 统一生成接口、任务查询与取消接口（含请求 / 响应结构、状态枚举、错误码） | OpenAPI 文档 + 示例响应 |
| 冻结三 | W7 末 | 会话与消息接口 | OpenAPI 文档 + 示例响应 |

冻结后如需变更，必须同步通知前端并更新文档；**不允许**只改后端不改文档。

### 6.2 Mock 与并行开发

- W3 起前端使用 Mock 服务（按冻结二的 OpenAPI 生成）独立开发，不等后端联调；
- 后端在 W4 内提供可用的联调环境（`docker-compose` 一键拉起）；
- 前后端每周至少一次接口对齐，对齐结论写入进度记录。

### 6.3 前端必须遵守的两条硬约束

1. **不向用户暴露细分生成类型**：前端只提交「生成图片 / 生成视频」+「是否上传素材」+「视频子模式」，具体 `task_type` 由后端推断。前端不得出现 txt2img、vid2vid 等内部术语；
2. **模型下拉只展示后端返回的启用模型及其支持档位**：前端不得硬编码任何模型名称、档位或价格。
